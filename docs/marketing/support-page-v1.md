# FrankBoard — Support Page Structure v1

**Date**: 2025-03-15  
**Status**: Strategy document  
**Scope**: Support page purpose, channels, tiers, page structure.

---

## Support Page Purpose

- Set clear expectations for Community vs Pro vs Cloud support.
- Direct users to the right resource (docs, GitHub, email).
- Position paid support as a legitimate option without pressuring Community users.
- Reduce support burden by surfacing self-serve options first.

---

## Support Channels / Tiers to Present

| Tier | Audience | Channel | Response |
|------|----------|---------|----------|
| **Self-serve** | All users | Docs, GitHub, community | Best-effort, community-driven |
| **Community** | Community edition users | GitHub issues, community channels | No SLA; community and maintainers respond when able |
| **Pro** | Pro subscribers | Email support | Priority SLA (when Pro is live) |
| **Cloud** | Cloud subscribers | Email + in-app | Included with subscription |

---

## Self-Serve Support Structure

1. **Documentation**
   - Getting started (install, Docker, first project)
   - Deployment guide (VPS, env vars, reverse proxy)
   - Migration from Kanboard
   - Link to Kanboard docs for app behavior

2. **GitHub**
   - Issues for bugs and feature requests
   - Discussions (if enabled) for questions
   - Clear contribution guidelines

3. **Community channels**
   - If a forum/Discord exists: link here
   - If not yet: "Community support via GitHub issues"

4. **Troubleshooting**
   - Common setup issues (DB connection, permissions)
   - Plugin compatibility notes
   - "Can't find it? Open an issue."

---

## Paid Support Positioning

- **Pro**: "Pro includes priority email support and a defined response-time SLA. For teams that need assurance."
- **Cloud**: "Cloud includes support as part of your subscription. We run it; we fix it."
- **Services**: "Need migration help or deployment setup? We offer project-based assistance. Contact us."

Do not:
- Imply Community users are second-class
- Pressure Community users to upgrade for basic help
- Promise response times before capacity exists

---

## Page Section Recommendations

1. **Header**: "Support when you need it"
2. **Self-serve first**
   - Documentation (links)
   - GitHub (issues, discussions)
   - Troubleshooting / FAQ
3. **By edition**
   - Community: Self-serve, GitHub, community
   - Pro: Priority support (when available)
   - Cloud: Included support
4. **Services**
   - Migration assistance
   - Deployment setup
   - Training
5. **Contact**
   - Pro/Cloud: support email
   - Services: contact form or email
6. **Footer CTA**: "Start with Community" / "Need Pro or Cloud? Contact us"

---

## Tone and Expectations

- **Transparent**: Say what we can and can't do. No overpromising.
- **Helpful**: Self-serve options are prominent. We want users to succeed without contacting us when possible.
- **Respectful**: Community users get clear paths; paid support is positioned as an option, not a requirement.
